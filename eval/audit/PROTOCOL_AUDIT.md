# Knowledge-base audit study — pre-specified protocol (written 2026-10-28, before any run)

Purpose: turn the registry-fidelity work of releases 15.0.0/15.1.0 into a validated, reusable method with
ground-truth evidence. Three parts, run in the order 2 → 1 → 3. Engine `analyse_gidlines.py` (v8.2) is not
modified anywhere in this study; registry 15.1.0 is the subject; v7 / 14.1.0 paper numbers are untouched.
Nothing here is tuned on benchmark labels; every outcome is reported whichever direction it goes.

## Part 2 — Verified-core sufficiency

Question. Is the engine's output attributable to rules with verified provenance, or does it depend on the
unverified AI-drafted mass?

Arms (registry only differs; same engine, same inputs, `--encounter icu` / `community`):
- FULL = registry 15.1.0 (31,070 executable rules).
- CORE = FULL with every rule made non-executable EXCEPT: status `curated_*` (anchors, 284),
  rules with `provenance.verified_quote` (37), rules whose first source is `reference_interval_convention` (36).
  Expected size ≈ 350 rules. Engine built-ins (ESL layer, WHO anaemia built-in rules) are part of the engine and
  stay on in both arms — stated as a limitation.
- The existing v7 `anchor_only` ablation (272 anchors) is cited for context, not re-run.

Corpora. eICU-CRD demo 2,314 stays (2,432 coded labels); NHANES 2017–18, 1,000 adults; healthy sweep n=200.

Pre-specified outcomes. Paired stay×label gains/losses at k = 1, 3, 5, 10 (flat and grouped) with exact sign
test; per-group AUROC; NHANES AUROC per task; false-assertion rate in guideline-healthy adults.
"Load-bearing fraction" of the unverified mass = FULL − CORE recall@k (percentage points, with the paired counts).
Interpretation rule, fixed now: |Δ| ≤ 1.0 pt at @5 and @10 → the unverified mass is not load-bearing;
1–3 pts → partially load-bearing (report which groups); > 3 pts → load-bearing (the sufficiency claim fails and is
reported as failing). No threshold or weight is changed in response to the result.

## Part 1 — Seeded-defect (mutation) validation of the static audit

Question. How sensitive and how specific is the rule-text audit (classes R2a, R2b-type contradictions, R7, R9,
plus unit/sex/operator checks) when the truth is known?

Seed set. All executable rules with `provenance.verified_quote` or status `curated_*` and a numeric leaf
(expected ≈ 300). These are the only rules whose thresholds are backed by a quote or by prior curation, so a
mutation of them is a defect by construction.

Mutation operators (one per mutant; each applied to every eligible seed rule; mutants are written to a separate
file, never into the live registry):
- M1 threshold ×1.5 / ×0.5 (arithmetic tier) — expected detector R7-style (requires a sibling screening rule;
  for seeds without one the detector is expected to MISS; recorded as such)
- M2 threshold ±10 % (subtle drift) — expected to be MISSED by the static audit; included to measure the floor
- M3 operator flip (< ↔ >) against the analyte's physiological direction — detector: direction check vs the
  feature registry's reference interval (new, specified here: a "<" rule whose threshold is above the upper
  reference limit, or ">" below the lower limit, is flagged)
- M4 unit swap mg/dL ↔ mmol/L (value kept) — detector: unit/value plausibility vs feature registry range
- M5 population swap (adult-only rule → includes neonate/infant) — detector: paediatric-limit check
  (only for analytes with documented paediatric limits; otherwise MISS)
- M6 analyte substitution to a ubiquitous marker on a clinical entity (e.g. replace the defining analyte by CRP)
  — detector R2a-wide
- M7 sign-impossible value (threshold ≤ 0 for a non-negative analyte) — detector R9
- M8 source swap to a topic-mismatched source id — detector: source-topic concordance (keyword match between
  source title/domain and feature/disease domain; specified in `audit.py`)

Metrics. Per operator: recall = detected mutants / mutants. Specificity: the detectors are run on the
*unmutated* seed set; any flag on an unmutated verified rule is a false positive (specificity = 1 − FP/seeds).
Also reported: overall recall, recall by analyte family, the confusion between classes (a mutant caught by the
"wrong" detector counts as detected but is tabulated).
Fixed in advance: detectors are frozen before mutants are generated (code committed first); no detector is
edited after seeing the mutant results. If a detector bug is found, it is fixed, the fix is logged, and the whole
mutation run is repeated and reported as a second round.

## Part 3 — Application to an independent LLM-authored rule set

Question. Are the defect classes specific to Hemoglyph's pipeline, or a general property of LLM-drafted
clinical rules?

Corpus. A fresh rule set of 200 entities (stratified: 60 infectious, 40 haematological, 30 renal, 30 endocrine,
40 other) generated by a frontier LLM with the fixed prompt in `eval/audit/llm_prompt.txt`, in the Hemoglyph
rule schema, WITHOUT the audit code or any defect list in context. Honest limitation, stated in advance: the
generating model is of the same vendor class used elsewhere in the paper and the generation is author-run; this
is a second LLM-authored corpus, not a third-party knowledge base. The generated file is frozen (SHA-256 recorded)
before the audit runs.

Outcome. Defect density per class (per 100 rules) with Wilson 95 % CI, compared with the Hemoglyph 14.1.0 and
15.1.0 densities computed by the same code. Side-by-side only; no significance claim across corpora of different
construction.
